# Nocturne — Frontend (Flutter)

Клиент Nocturne (mobile + web) — платформы визуальных новелл с ИИ-персонажами, из единой
Flutter-кодовой базы, работающий против Core Backend (Go) из соседнего репозитория
`vn_startup_core_backend_go`. У AI Orchestrator (Python) нет публичного API, и это приложение
никогда не обращается к нему напрямую — весь сетевой доступ идёт через REST- и
WebSocket-эндпоинты Core Backend.

## Требования

- Flutter (stable-канал, Dart >=3.12.2 — см. `environment.sdk` в `pubspec.yaml`)
- Локально запущенный Core Backend (см. `vn_startup_core_backend_go/README.md`) — без него
  работает только экран авторизации, всё остальное требует реального API

## Настройка окружения

Нигде в приложении нет захардкоженного конфига — каждое зависящее от окружения значение
(URL API, таймауты, размер страницы, флаги фич, наборы алмазов, список жанров) читается один
раз в `main.dart` через `AppConfig.fromEnvironment()` и прокидывается через
`ProviderScope(overrides: [...])`. Чтение `appConfigProvider` до того, как это переопределение
подключено, намеренно бросает `UnimplementedError` — это защита «громко упасть», а не
недоделанная заглушка.

В `config/` лежат три примера файлов окружения:

- `config/.env.dev.example.json`
- `config/.env.staging.example.json`
- `config/.env.prod.example.json`

Скопируйте нужный (без `.example`) и при необходимости отредактируйте значения:

```bash
cp config/.env.dev.example.json config/.env.dev.json
```

| Ключ | Значение |
|---|---|
| `APP_NAME` | Отображаемое имя (по умолчанию `Nocturne`) — меняется в одном месте, а не по виджетам |
| `APP_ENV` | `development` \| `staging` \| `production` |
| `API_BASE_URL` | Базовый URL REST API Core Backend |
| `WS_BASE_URL` | Базовый URL WebSocket Core Backend (`GET /ws`) |
| `API_TIMEOUT_MS` | Таймаут подключения/ответа Dio |
| `TOKEN_REFRESH_MARGIN_MS` | За сколько до истечения access-токена начинать silent refresh |
| `STORIES_PAGE_SIZE` | Размер страницы каталога историй |
| `DEFAULT_LOCALE` | `ru` или `en` |
| `SUPPORTED_LOCALES` | Список локалей через запятую |
| `DEFAULT_THEME_MODE` | `dark` \| `light` \| `system` |
| `ENABLE_DEV_WALLET_GRANT` | Зеркалит `ENABLE_DEV_ENDPOINTS` бэкенда — включает dev-кнопку «начислить алмазы» в магазине (см. «Известные ограничения») |
| `TERMS_PRIVACY_URL` | Внешняя ссылка, открываемая из Настроек → О приложении |

Наборы алмазов и канонический список жанров **не** зависят от окружения — это статичный
Dart-конфиг (`AppConfig.diamondBundles` в `lib/core/config/app_config.dart`,
`lib/core/constants/genres.dart`), поскольку у бэкенда пока нет эндпоинта каталога/бандлов (см.
«Известные ограничения»). Чтобы поменять цену бандла или добавить жанр — редактируйте эти файлы
напрямую.

## Запуск

Флейворы (`dev` / `staging` / `prod`) нативно настроены на Android (`applicationIdSuffix`,
имя приложения на флейвор) и читают соответствующий `config/.env.<flavor>.json` через
`--dart-define-from-file`:

```bash
flutter pub get
flutter run --flavor dev --dart-define-from-file=config/.env.dev.json
```

Для web (флейворов нет, просто указываете файл конфига):

```bash
flutter run -d chrome --dart-define-from-file=config/.env.dev.json
```

Само по себе это запускает только UI — чтобы что-то, кроме экрана авторизации, заработало,
нужен поднятый бэкенд. Ниже — пошаговая инструкция именно на этот случай.

## Как подключить фронтенд к локальному бэкенду (устранение ошибки подключения)

Если приложение показывает ошибку сети/подключения при попытке зарегистрироваться или войти —
почти всегда причина в одном из шагов ниже, а не в самом фронтенде. Пройдите их по порядку.

### 1. Поднять Core Backend

В соседнем репозитории `vn_startup_core_backend_go`:

```bash
cd ../vn_startup_core_backend_go
cp .env.example .env
make up          # поднимает Postgres, Redis, NATS через docker-compose (нужен запущенный Docker)
make migrate      # накатывает все миграции
make seed         # засевает пару тестовых историй — без этого каталог будет пустым
make run          # собирает и запускает API
```

Если команды `make`/`migrate` не установлены отдельно (на Windows это не входит в стандартный
набор) — либо поставьте их (`choco install make`, `go install
github.com/golang-migrate/migrate/v4/cmd/migrate@latest`), либо выполните эквивалентные команды
напрямую — они перечислены в `vn_startup_core_backend_go/Makefile`.

В терминале должна появиться строка вида:

```
level=INFO msg="http server listening" addr=:8080 env=development
```

Это значит, что API поднялся и слушает `http://localhost:8080` (порт настраивается через
`SERVER_PORT` в `.env`). Держите это окно терминала открытым — при закрытии сервис остановится.

**Быстрая проверка, что бэкенд действительно отвечает** (в отдельном терминале):

```bash
curl -i http://localhost:8080/stories
```

Ответ `401 unauthorized` (а не «Connection refused»/таймаут) — это нормально и означает, что
сервер жив и просто требует токен; сетевого пути «фронтенд ↔ бэкенд» это уже касается.

### 2. Настроить фронтенд на этот адрес

Значения по умолчанию в `config/.env.dev.example.json` (`API_BASE_URL=http://localhost:8080`,
`WS_BASE_URL=ws://localhost:8080`) уже совпадают с портом бэкенда по умолчанию — если вы не
меняли `SERVER_PORT`, отдельно ничего настраивать не нужно:

```bash
cp config/.env.dev.example.json config/.env.dev.json
```

### 3. Запустить фронтенд с этим конфигом

```bash
flutter run --flavor dev --dart-define-from-file=config/.env.dev.json -d <устройство>
```

(`flutter devices` покажет список доступных `<устройство>` — веб-браузер, desktop, эмулятор
или подключённый телефон, см. следующий раздел).

### 4. Проверить, что соединение реально работает

На экране авторизации переключитесь на вкладку «Регистрация», введите любой email/пароль и
нажмите кнопку. Если через мгновение вас перекинуло в онбординг — соединение работает. Если
вместо этого показывается ошибка сети под полями формы — переходите к таблице ниже.

### Типичные причины ошибки подключения

| Симптом | Причина | Что делать |
|---|---|---|
| Мгновенная ошибка сети на любом действии | Бэкенд не запущен или упал | Проверить терминал с `make run` — если процесс завершился, перезапустить; убедиться, что Docker Desktop запущен для `make up` |
| `Connection refused` при `curl http://localhost:8080/...` | Контейнеры Postgres/Redis/NATS не подняты | `docker ps` — должно быть 3 контейнера; если пусто, выполнить `make up` заново |
| Ошибки 500 на любом запросе, требующем данные (`/stories` и т.д.) | Миграции не накатаны | `make migrate` |
| Каталог историй пустой, но ошибок нет | Не выполнен `make seed` | `make seed` (идемпотентно, безопасно перезапускать) |
| В браузере (Chrome/Edge, `flutter run -d chrome`/`-d edge`) ошибка сети, хотя curl/desktop/телефон работают | Бэкенд запущен на **старом бинарнике**, собранном до того, как в Core Backend добавили CORS-middleware (см. ниже) — без CORS браузер блокирует кросс-доменный запрос с dev-сервера Flutter web на `localhost:8080` ещё на своей стороне, а Dio показывает это как обычную сетевую ошибку, не как CORS-ошибку | Пересобрать и перезапустить бэкенд: `make run` (или вручную `go build -o bin/api ./cmd/api && ./bin/api`) — CORS включён по умолчанию (`CORS_ALLOWED_ORIGINS=*`), но только в актуальной сборке. Если ошибка сохранилась — проверьте вкладку Network в DevTools: `OPTIONS`-запрос на `/auth/...`, вернувший не `204`, означает, что `CORS_ALLOWED_ORIGINS` в `.env` бэкенда переопределён на что-то более строгое |
| Работает в браузере/desktop на этом же ПК, но не на телефоне | `localhost` на телефоне — это сам телефон, а не ваш ПК | См. раздел «Запуск на Android-телефоне» ниже — там отдельно про адрес backend'а для реального устройства |
| `ENABLE_DEV_ENDPOINTS`-эндпоинт (`/dev/wallet/grant`, кнопка покупки в dev-режиме) возвращает 404 | В `.env` бэкенда `ENABLE_DEV_ENDPOINTS=false` (или не задан) | Выставить `ENABLE_DEV_ENDPOINTS=true` в `.env` бэкенда и перезапустить `make run` |

Core Backend по умолчанию разрешает запросы с любого origin (`CORS_ALLOWED_ORIGINS=*` в
`.env.example`) — это безопасно, поскольку авторизация идёт через `Authorization: Bearer`, а не
через cookie, так что wildcard-origin не даёт возможности угонять чужую сессию. В
staging/production сузьте `CORS_ALLOWED_ORIGINS` до реального адреса задеплоенного фронтенда.

## Как запустить на Android-телефоне

Помимо стандартных шагов «Как подключить фронтенд к локальному бэкенду» выше, реальное
устройство требует ещё двух вещей, которых desktop/эмулятор не требуют: правильного сетевого
адреса до бэкенда на вашем ПК и разрешения на нешифрованный (`http://`, не `https://`) трафик —
без этого Android **гарантированно** заблокирует запрос ещё до выхода в сеть.

### 1. Подготовка

- Установленный Android Studio с Android SDK и `platform-tools` (в частности, `adb`) —
  `flutter doctor` должен показывать зелёную галочку у Android toolchain.
- На телефоне: Настройки → О телефоне → 7 раз нажать «Номер сборки», чтобы включить «Для
  разработчиков», затем Настройки → Для разработчиков → включить «Отладка по USB».
- Телефон подключён к ПК USB-кабелем. При первом подключении на экране телефона появится
  запрос «Разрешить отладку по USB с этого компьютера?» — обязательно подтвердите (иначе `adb`
  и `flutter` устройство не увидят).

Проверить, что устройство определилось:

```bash
flutter devices
```

Телефон должен появиться в списке с типом `mobile`, `android-arm64` (или похожим). Если нет —
`adb devices` должен показывать его в статусе `device` (не `unauthorized`/`offline`); если
`unauthorized` — проверьте экран телефона на всплывающий запрос подтверждения.

### 2. Дать телефону доступ к бэкенду, работающему на вашем ПК

`localhost`/`127.0.0.1` в конфиге фронтенда указывает на «текущее устройство» — на телефоне это
сам телефон, а не ваш компьютер, поэтому конфиг для desktop/эмулятора на телефоне не заработает
без изменений. Есть два рабочих способа, выберите один.

**Способ А — `adb reverse` (рекомендуется, проще всего, не требует Wi-Fi)**

Пробрасывает порт `8080` телефона на порт `8080` вашего ПК через сам USB-кабель — конфиг
фронтенда можно вообще не менять, `http://localhost:8080` в `config/.env.dev.json` будет
работать и с телефона:

```bash
adb reverse tcp:8080 tcp:8080
```

Проброс живёт, пока телефон подключён по USB и `adb`-сервер не перезапускался; после
переподключения кабеля команду нужно выполнить заново.

**Способ Б — IP адрес ПК в локальной сети (нужен, если хотите отлаживаться по Wi-Fi без кабеля)**

1. Узнать IP-адрес ПК в локальной сети:

```bash
ipconfig
```

Найти секцию активного адаптера (Wi-Fi или Ethernet) и значение `IPv4 Address`, например
`192.168.1.23`.

2. Убедиться, что телефон и ПК в одной Wi-Fi-сети.

3. Создать отдельный конфиг с этим адресом (не редактируйте `config/.env.dev.json` напрямую,
   чтобы не потерять адрес `localhost`, нужный для desktop/эмулятора):

```bash
cp config/.env.dev.example.json config/.env.dev.phone.json
```

и в `config/.env.dev.phone.json` заменить:

```json
"API_BASE_URL": "http://192.168.1.23:8080",
"WS_BASE_URL": "ws://192.168.1.23:8080",
```

(подставив свой реальный IP).

4. Разрешить входящие подключения на порт 8080 в брандмауэре Windows — по умолчанию Windows
   блокирует незапрошенные входящие соединения к незарегистрированным приложениям:

```powershell
New-NetFirewallRule -DisplayName "Nocturne backend dev" -Direction Inbound -LocalPort 8080 -Protocol TCP -Action Allow
```

(команда должна выполняться из PowerShell с правами администратора).

**Способ В — Android-эмулятор (AVD), а не реальный телефон**

Для эмулятора не нужен ни `adb reverse`, ни IP из локальной сети: специальный псевдоним
`10.0.2.2` в сети эмулятора всегда указывает на `localhost` хост-машины. Готовый конфиг уже
есть в репозитории — `config/.env.dev.emulator.json` (`API_BASE_URL`/`WS_BASE_URL` =
`http://10.0.2.2:8080`/`ws://10.0.2.2:8080`), используйте его вместо `config/.env.dev.json` при
запуске на эмуляторе (см. шаг 4 ниже). Обычный `config/.env.dev.json` с `localhost` на
эмуляторе **не сработает** — `localhost` там указывает на сам эмулятор, а не на ваш ПК, и
приложение покажет ту же ошибку сети, что и при попытке зарегистрироваться без бэкенда вовсе.

### 3. Разрешение на нешифрованный (`http://`) трафик

Начиная с Android 9 (API 28), ОС по умолчанию блокирует любой `http://`-трафик (не `https://`) —
а Core Backend в локальной разработке всегда `http://`, TLS-сертификата нет и не предполагается.
Без явного разрешения запрос до бэкенда не дойдёт вообще, с ошибкой вида
`ERR_CLEARTEXT_NOT_PERMITTED`, — это, вероятно, самая частая причина «не подключается» именно на
реальном устройстве/эмуляторе (в отличие от desktop/web, где такого ограничения нет).

Это уже настроено в проекте и не требует ручных действий: `android/app/src/debug/` и
`android/app/src/profile/` содержат `res/xml/network_security_config.xml`
(`cleartextTrafficPermitted="true"`), подключённый только к debug- и profile-сборкам через
`android:networkSecurityConfig` в соответствующих `AndroidManifest.xml`. Обычный запуск через
`flutter run` (debug-режим по умолчанию) получит это разрешение автоматически. Release-сборка
(`flutter build apk --release`) его **не** получает намеренно — в проде бэкенд должен быть на
`https://`, и там cleartext-трафик остаётся заблокированным, как и должно быть из соображений
безопасности.

### 4. Запуск

Реальный телефон, способ А (`adb reverse`):

```bash
flutter run --flavor dev --dart-define-from-file=config/.env.dev.json -d <id-телефона>
```

Реальный телефон, способ Б (IP в локальной сети) — используйте `config/.env.dev.phone.json`
вместо `config/.env.dev.json`. Android-эмулятор, способ В — используйте
`config/.env.dev.emulator.json`:

```bash
flutter run --flavor dev --dart-define-from-file=config/.env.dev.emulator.json -d emulator-5554
```

`<id-телефона>`/`emulator-5554` — из вывода `flutter devices`; если подключено единственное
устройство, флаг `-d` можно опустить.

Первая сборка debug-APK может занять несколько минут. Дальше действует hot reload — как и на
любом другом устройстве.

### Типичные ошибки именно на Android

| Симптом | Причина | Что делать |
|---|---|---|
| `Product Flavor dev contains custom resource values, but the feature is disabled` при сборке (ещё до установки на устройство/эмулятор) | Начиная с AGP 8+ (в проекте — AGP 9.0.1, см. `android/settings.gradle.kts`), фича `resValues` отключена по умолчанию, а `android/app/build.gradle.kts` использует `resValue(...)` на каждом флейворе для имени приложения | Уже исправлено — в `android/app/build.gradle.kts` добавлен блок `buildFeatures { resValues = true }`. Если ошибка повторяется — убедитесь, что используете актуальную версию файла |
| `Could not close incremental caches ... this and base files have different roots: C:\...\pub.dev\...` при `compileDebugKotlin` (обычно на нескольких плагинах сразу — `package_info_plus`, `url_launcher_android`, `shared_preferences_android`) | Windows-специфичный баг Kotlin-компилятора: incremental-кэш пытается выразить путь до исходников плагина (в pub cache) относительно каталога проекта — если проект и pub cache/Gradle-кэш лежат на **разных дисках** (например, проект на `D:`, а профиль пользователя и `%LOCALAPPDATA%\Pub\Cache` — на `C:`), у путей нет общего корня и вычисление ломается | Уже исправлено — в `android/gradle.properties` добавлено `kotlin.incremental=false`, это отключает incremental-компиляцию Kotlin целиком (пересборка чуть медленнее, но плагины — крошечные Kotlin-шимы, разница не заметна) |
| Телефон не появляется в `flutter devices` | Не подтверждена отладка по USB на самом телефоне, либо не установлены USB-драйверы | Проверить экран телефона на запрос подтверждения; `adb devices` — статус должен быть `device` |
| `ERR_CLEARTEXT_NOT_PERMITTED` в логах `flutter run` | Собрана release-сборка (`--release`), а не debug — cleartext-разрешение туда намеренно не попадает | Для локальной разработки против `http://`-бэкенда используйте debug/profile (`flutter run` без `--release`) |
| `Connection refused`/таймаут только с телефона, а с ПК всё работает | Забыт `adb reverse` (Способ А) после переподключения кабеля, либо неверный/устаревший IP (Способ Б), либо брандмауэр блокирует порт | Повторить `adb reverse tcp:8080 tcp:8080`, либо перепроверить `ipconfig` и правило брандмауэра |
| Работает дома по Wi-Fi, перестаёт — в другой сети | Способ Б завязан на текущую локальную сеть и IP ПК в ней, который на другой сети меняется | Переключиться на Способ А (`adb reverse`, работает всегда через USB независимо от Wi-Fi) |

## Кодогенерация

Freezed-модели, JSON-сериализация и кодоген Riverpod — всё через `build_runner`. Перезапускайте
после правок любого `*.freezed.dart`/`*.g.dart`-источника или после получения изменений,
затрагивающих модели/провайдеры:

```bash
dart run build_runner build --delete-conflicting-outputs
```

## Тестирование

```bash
flutter analyze                           # строгие линты, должно быть чисто
flutter test                              # unit/widget/golden-тесты
flutter test integration_test -d <устройство>  # сквозной флоу, нужно реальное устройство
```

`integration_test/app_flow_test.dart` покрывает золотой путь — вход, открытие истории, разговор
с персонажем в свободном диалоге, отправка сообщения, получение потокового ответа, затем
бесплатный выбор и переход на следующую сцену — подменяя репозитории auth/story/wallet/dialog и
`webSocketClientProvider` напрямую моками, поэтому реальный бэкенд или настоящий WebSocket-сервер
не нужны. А вот работающая цель запуска — нужна: `-d chrome` runner `integration_test`
отклоняет («Web devices are not supported for integration tests yet»), а `-d windows`/`-d
android`/`-d ios` требуют реального тулчейна своей платформы (Visual Studio с C++ workload;
Android SDK + эмулятор; Mac с Xcode) для сборки и запуска приложения. Ничего из этого не было
доступно в окружении, где писался этот тест, поэтому он проверен `flutter analyze` (компилируется
без ошибок против реальных интерфейсов провайдеров/репозиториев), но не прогонялся целиком здесь
— запустите его там, где доступно реальное устройство/эмулятор/тулчейн.

Golden-тесты лежат в `test/golden/` (обе темы для Auth, Settings, Stories, Story Detail, Shop,
Profile, плюс каждое состояние `MessageBubble` и все четыре причины `SessionEndedDialog`). Если
golden-тест падает после намеренного визуального изменения — перегенерировать:

```bash
flutter test --update-goldens
```

### Web-сборка

Прод-сборки веба используют WasmGC:

```bash
flutter build web --wasm
```

Экран `scene_player` — зона наибольшего риска по производительности в вебе (единственный экран
со слоистой сценой на кастомной отрисовке), поэтому после любых изменений в этой фиче отдельно
перепроверяйте там таймингы кадров, а не только то, что сборка прошла.

## Архитектура

Feature-first, три слоя на фичу в `lib/features/<name>/`:

- `presentation/` — экраны, виджеты, Riverpod-провайдеры. Только `ConsumerWidget`/
  `ConsumerStatefulWidget`; `setState` — только в чисто визуальных листовых виджетах (например,
  собственная scale-анимация нажатия кнопки).
- `domain/` — freezed-модели, тонкие use-case классы там, где поверх сырого запроса есть
  реальная логика.
- `data/` — интерфейс репозитория + реализация поверх написанного вручную Dio API-класса (см.
  ниже).

Общий код — в `lib/core/`: конфиг, токены темы (`ThemeExtension<AppColors>`, типографика,
константы в `motion.dart`), роутинг (go_router + auth guard), сеть (Dio-клиент, auth-интерцептор,
error mapper, WebSocket-клиент), secure storage и «глупые» переиспользуемые виджеты.

**Отклонение от retrofit:** в спецификации просили retrofit-генерируемые API-клиенты; здесь
вместо этого — написанные вручную Dio-обёртки на каждую фичу (см. doc-комментарий на `AuthApi`).
Кодоген retrofit сидел бы в том же пайплайне `build_runner`, что и
riverpod_generator/freezed/json_serializable, а точная комбинация версий пакетов, при которой
этот граф вообще разрешается на pub.dev сегодня, и так потребовала не самого очевидного пиннинга
(см. заметку про Riverpod ниже) — добавлять поверх ещё retrofit_generator не стоило той
хрупкости ради горстки простых REST-методов на фичу. Поведение идентично в обоих случаях:
типизированные модели запроса/ответа, один класс на эндпоинты фичи.

**Версия Riverpod:** проект зафиксирован на `flutter_riverpod`/`riverpod_annotation` **2.6.1**, а
не на Riverpod 3. На момент написания `riverpod_annotation >=4.0.6` тянет `riverpod 3.4.2`,
который зависит от `test ^1.0.0` — это конфликтует с точными версиями `matcher`/`test_api`,
которые фиксирует встроенный в установленный Flutter SDK пакет `flutter_test`, в сочетании с
зависимостью проекта `web_socket_channel ^3.0.3`. Solver pub не может удовлетворить все три
одновременно, как ни закрепляй версии остального графа. `riverpod_generator 2.3.9` (в паре с
`riverpod_annotation 2.6.1`) — самая новая взаимно совместимая комбинация из найденных; она, в
свою очередь, требует `source_gen 1.5.0`, который требует `json_serializable
6.6.2`/`json_annotation 4.8.1`. При будущем апгрейде любого из этого — пересчитывайте всю цепочку
заново, а не поднимайте версии по одной: они взаимосвязаны, а не независимы друг от друга.

## Известные ограничения

Это намеренные, честно обозначенные отступления от исходной спецификации, а не молчаливые
заглушки. Каждое видно в UI как состояние «скоро»/отключённый элемент, а не как выдуманные
данные, и закомментировано прямо в коде на своём месте:

- **Гостевой режим** (`features/auth`) — полностью на стороне клиента: у Core Backend нет
  эндпоинта анонимной сессии. Гостю доступен только просмотр каталога; любое платное
  действие/действие с библиотекой предлагает зарегистрироваться.
- **Пагинация и фильтр по жанру каталога историй** (`stories_providers.dart`) — только на
  стороне клиента. `GET /stories` сегодня отдаёт весь список без параметров `page`/`genre` на
  бэкенде, поэтому «бесконечный скролл» на самом деле пагинирует уже полностью загруженный
  список в памяти через `AppConfig.storiesPageSize`, а чипы жанров фильтруют тот же список на
  клиенте. Когда бэкенд добавит эти параметры — заменить на реальную серверную
  пагинацию/фильтрацию, граница провайдера уже под это рассчитана.
- **Закладки** (`local_bookmarks_provider.dart`) — только локальные (SharedPreferences); у
  бэкенда пока нет эндпоинта вида `POST /stories/:id/bookmark`.
- **Статистика профиля**: `finished` (завершённые истории) и `diamonds` честно считаются из
  реальных данных (`player_progress` + баланс кошелька). `day_streak` и `hours_read` показывают
  состояние «скоро» (`comingSoon: true`, без выдуманного числа), поскольку у бэкенда нет модуля
  трекинга стрика/времени чтения. **Достижения** по той же причине рендерятся как настоящее
  пустое состояние — без захардкоженного списка чипов — до появления бэкенд-источника данных.
- **Покупки в магазине** (`shop_screen.dart`) вызывают `POST /dev/wallet/grant` — dev-only
  эндпоинт, включаемый через `AppConfig.enableDevWalletGrant` (зеркалит бэкендовый
  `ENABLE_DEV_ENDPOINTS`) — вместо реального платёжного флоу, поскольку у Core Backend
  намеренно ещё нет платёжной интеграции. Это отмечено явным `TODO` у кнопки покупки, а сама
  подпись кнопки говорит «(dev mode)» вместо реальной цены.
- **Смена пароля** (`features/settings`) — реальная форма, но кнопка сохранения отключена с
  поясняющей подписью: модуль `internal/auth` бэкенда пока отдаёт только
  регистрацию/логин/рефреш, эндпоинта смены пароля ещё нет.
- **Управление подпиской** (`features/settings`) честно показывает состояние «пока
  недоступно» — таблицы/модуля `subscriptions` в Core Backend не существует.
- **Верхняя панель сцены** (`scene_top_bar.dart`) — кнопки автопрокрутки и пропуска видимо
  присутствуют, но отключены с `TODO` до появления дизайна темпа воспроизведения; лог/история
  реплик реализованы полностью.
